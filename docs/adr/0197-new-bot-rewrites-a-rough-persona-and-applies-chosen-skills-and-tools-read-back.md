# New bot rewrites a rough persona and applies chosen skills and tools, read back

> **Partly superseded by [ADR 0204](0204-a-persona-is-edited-only-in-the-profile-form-and-write-with-ai-rewrites-it-in-place.md).** Generate with AI is now Write with AI, on New and Edit, and puts its answer in the Persona field with Undo instead of a suggestion box with Replace persona and Discard; Create waits only while it runs. Edit has the Persona field itself, not a link to Settings → Persona, which is gone. The rest of this ADR stands.
>
> **Accepted.** It adds to ADR 0164 (New bot is the New profile form) and follows ADR 0074's clone stages and ADR 0152's one-off calls. The form is `ProfileForm` in `src/ui/ProfileSettings.tsx`, with `src/ui/PersonaRephrase.tsx` and `src/ui/BotCapabilities.tsx`. The calls are `src/hermes/personaRephrase.ts` and `src/hermes/botSetup.ts`. The relay rule `profile_create_allowed` in `src-tauri/src/transport.rs` is unchanged. Tested in `src/hermes/personaRephrase.test.ts`, `src/hermes/botSetup.test.ts`, `src/ui/botCreation.test.tsx` and `src/ui/bots.test.tsx`.

The New profile form, which is also the Bots view's New bot (ADR 0164), made a profile from a name, a description, a model and an optional persona. The owner wanted to type a rough persona and have the configured AI tidy it up, and to pick the bot's skills, tools and MCP integrations before creating it.

## Owner decisions

The owner delegated these calls on 2026-11-17 ("do what you think is best"). They are recorded here as decided on the owner's behalf.

1. **Hermes has no create that sets everything at once.** The create carries what Hermes takes in it; the rest is applied after, as tracked stages read back from the new profile. When anything isn't as chosen, the dialog lists what is and isn't applied and offers **Delete <name>** (only when Hermes answered the create) or **Keep it as is**. A partial result never shows a success notice. This is ADR 0074's clone precedent.
2. **MCP servers are left out of creation.** A note says why and points to Settings → MCP servers after creating. It is an open gap; see below.
3. **Skills are the built-in set a new profile starts with, kept or turned off**, then read back. The first build sent the choice in the create as `keep_skills` or `no_skills`; against a real Hermes that turned off skills the owner was never shown, so the choice is now applied after the create, one skill at a time (see Considered options).

## Decisions

### Generate with AI only rewrites what the owner typed

- **A button beside Persona, on New only.** Edit keeps its link to Settings → Persona.
- **It never writes from nothing.** With an empty or blank box the button is off and says to type a rough persona first. It is also off, with its reason under the field, while the app isn't connected, without the call wired, while the model is read, when that read failed, and when the profile in use has no Text generation provider. The button stays focusable while off, so its reason is read with it (`aria-disabled` and `aria-describedby`).
- **One click, one call.** Hermes's stateless `llm.oneshot` (`Hermes.askForEdit`) with no tools and no chat. Its instructions tell the model to rewrite the owner's notes into the persona in the second person, keep every intent, constraint, name and the language, add no authority, permissions, tools, integrations, facts or rules, and treat the tagged text as data. At most 8000 characters are sent, and the suggestion says so when the persona was longer. A closing persona tag in the owner's text is turned into look-alike brackets, so the tagged data ends only where the owner's text does. An answer with no text is a failure, in the catalogue's words. A second click before the screen catches up sends nothing.
- **Which model.** The call runs as the profile in use (`wiring.inUse`) on its Text generation model (`TEXT_TASK`), which is what `ModelSettingsApi.textModel` reads. It is not the model picked for the new bot: that profile doesn't exist yet. The hint names it: "Rewritten by <model>, the Text generation model of <profile>".
- **The answer is a suggestion.** It shows in an editable box under the field, with **Replace persona** and **Discard**. Only Replace puts it in the persona box. If the box changed since the call was sent, the suggestion says so and the button reads **Replace anyway**. A failure, Stop and Discard leave the box as it was; a failure shows Hermes's words, and a missing sign-in says which model and setting, never a key.
- **Hermes has no cancel.** Stop, a newer click, closing the dialog and losing the connection drop the answer when it comes, and the form is ready again; the call may still finish on the server, and the hint while it runs says so. A call that runs past `ASK_DEADLINE_MS` fails.
- **Create waits.** It is off, with the reason, while a call runs or a suggestion is open, so a suggestion never reaches Hermes unless the owner applied it. An open suggestion counts as an unsaved change when leaving.

### Skills and Tools are Hermes's defaults unless chosen

- **Two choices per area: Hermes's defaults, or Choose.** Defaults is selected, and with it the create's body is byte for byte what it was before this change.
- **Choose reads what there is, then.** Skills lists the profile in use's built-in skills (`GET /api/skills`, `provenance: bundled`), labelled as the built-in skills that profile lists, since Hermes may seed others the list hides there; nothing else is offered. Every one starts on. `hermes-agent` is shown on and can't be turned off, since Hermes keeps it on. Tools lists the profile in use's toolsets and starts from what it has on, labelled so. A toolset whose name the app doesn't send (`changeableName`) is shown off-limits with why. Each list has a filter, a live count, All on and All off for what's shown, and checkboxes reached by Tab. A list that can't be read shows why with Try again, and the area stays on Hermes's defaults; a server without the route says it can't list them. Only the newest read counts: one that ends after Hermes's defaults were picked again, or after a newer read, changes nothing. When the profile in use changes while the form is open, a chosen list is read again from it, and Choose starts over from what that profile has on, with only the ticks the owner changed from the old start put back over it, so the hint "Starts from what <profile> has on" stays true. A line under the hint says when the new list doesn't list a name the owner changed, so that change was dropped, and when the list couldn't be read again or offers nothing, so the area went back to Hermes's defaults. An unchosen list is read on the next Choose, and Generate with AI reads that profile's Text generation model again, dropping a call still out.
- **The create carries nothing for them.** Its body is byte for byte what it was before this change, whatever is chosen. Toolsets aren't in Hermes's `ProfileCreate`, and skills are applied after (below). Hermes seeds its built-in skills into the new profile, all on.
- **Stages, only after Hermes answered.** (a) Skills: the new profile's skills are read (`GET /api/skills?profile=<new>`). Each skill of the list the owner chose from is judged by one rule, the same on the first apply and on Try again: chosen on, it must be listed and on; chosen off, it must be off or not listed. Each listed skill not as chosen is switched through Settings → Skills' own `SkillsApi.setEnabled` (`PUT /api/skills/toggle?profile=<new>`), which reads the list back. A skill the owner wasn't shown is never switched, so a built-in skill Hermes seeds but `GET /api/skills` hides stays as Hermes sets it. Turning every listed skill off ("All off") leaves those alone too. A listed skill whose name the app doesn't send (`safeSkillName`) is shown locked, with why, and isn't switched or checked; `hermes-agent` is shown locked on, and is only read back: if the new profile has it off, the outcome says so, and neither the first apply nor Try again switches it. (b) Tools: the new profile's toolsets are read, and each that differs from the choice is set with Settings → Toolsets' own `ToolsetsApi.set`, which checks it against a fresh read, re-checks its cautions, writes, and reads it back. The toolset list read is limited to 30 seconds and each change, with its reads, to 60, Settings → Skills' own limits (`TOOLSET_TIMEOUTS`), since `ToolsetsApi` sets none; the first apply and Try again use the same limits. A caution (an install, MCP coming back, a toolset turned off everywhere) is never accepted here: the item waits for **Apply anyway**, which sends it with those cautions accepted.
- **Nothing more once Hermes stops answering.** Skills and toolsets follow one rule. A call that got no answer (the connection gone or lost on the way, a deadline passed, a skill switch whose answer was lost while the list read after it doesn't show the change, or a toolset change Hermes didn't confirm with no answer behind it) fails its item with that reason, and every item after it fails as not tried, with that reason shown as the earlier call's own words, without a request. A call Hermes answered with an error (any status, a sign-in it turned down, a list this app can't read, a route the server lacks) fails only its own item, or, for an area's list read, that area's items, and the run goes on. Try again on any of them runs as the first apply did. While the stages run, the line under the form counts the items judged, and only the count ("n of m done") is announced as it changes.
- **The outcome is per item.** Each skill and toolset ends applied, failed with why, or waiting on a caution. A toolset Hermes saved as chosen keeps what else it did: an install it started, an error it answered anyway, `no_mcp` cleared, or the toolset taken off `agent.disabled_toolsets`. The outcome lists these under "Hermes also", and the closing notice repeats them. A success notice ("Created <name> with the skills and tools you chose.") comes only when every item read back as chosen and the model, if one was picked, was set. Otherwise the dialog stays open on what isn't applied, each with **Try again** (against a fresh read, as the first apply) or **Apply anyway**, and the profile's fate: **Delete <name>**, through the same delete as Delete profile and this computer's data for it, or **Keep it as is**, which closes with a notice in the bad tone naming what isn't as chosen. Delete's notice says what Delete profile's would: when this computer's data couldn't be removed, and when Hermes answers `settlement_pending`, that it hasn't finished cleaning up, with its `retry_command` to run and copy. When the model picked wasn't set, the outcome also offers **Set model…**, which closes with that notice and opens Edit, as a plain create does; the Bots view has no Edit to go on to, so it doesn't. Escape and a click outside don't close it. Once every item is applied, **Done** closes with the success notice.
- **One create per click.** A second activation of Create before the screen catches up sends nothing. Create stays focusable while it can't run, with its reason tied to it (`aria-disabled`, `aria-describedby`); so do the locked checkboxes. If the whole view closes after Create, the create and its stages still run, and what they came to reaches the owner through the app's own notice (`ProfilesWiring.notify`), since the view that would show it is gone. The same holds for a create Hermes refused, for Try again, and for the outcome's Delete, whether it went through or failed; every one ends through the form's one `finish`. The app shows these as its toast: a settling delete's command comes with the toast's **Copy command**, and a notice in the bad tone stays up as long as a toast with an action does.
- **A lost create answer.** When Hermes's answer was lost but it lists the profile, nothing more is written: the notice says the skills and tools weren't checked or changed, and where to see them. There is no Delete: the app can't tell what it made.

### MCP servers stay out, as an open gap

The New form says: "Highwing can't add MCP servers while creating a profile: Hermes would have to copy them without their secrets, and it has no way to yet. After creating, add them in Settings → MCP servers." There are no controls for them.

Evidence at Hermes `f0d94882`: `ProfileCreate` (`hermes_cli/web_models.py:454-472`) takes `mcp_servers` as `MCPServerCreate` entries (`web_models.py:359-368`), each carrying its `env` and `bearer_token` values. The catalog install (`hermes_cli/web_routers/mcp.py:471-540`, `mcp_catalog.py:772-817`) clones a repository, writes credentials and probes the server. Neither copies a server from another profile by reference. Offering MCP servers here would mean the app reading and sending their secrets, or starting installs, which the relay refuses (ADR 0074). What Hermes would need: a create field, or a route, that copies named MCP servers from a source profile on the server, secrets included, without them passing through the client.

### The relay is unchanged

`profile_create_allowed` still refuses `keep_skills`, `no_skills`, `mcp_servers`, `hub_skills`, `clone_all`, `clone_channels` and `clone_from_default` (ADR 0074). The skill switches go through `PUT /api/skills/toggle`, which the relay already passes for Settings → Skills.

## Considered options

- **Generate a persona from nothing (the name or description).** Rejected: the owner asked for a rewrite of their own text, and a persona the owner didn't write is one they haven't thought through.
- **Run the rewrite on the model picked for the new bot.** Rejected: the profile doesn't exist until Create, and `llm.oneshot` runs as an existing profile. Its Text generation model is what the profile in use already trusts for one-off calls.
- **Put the suggestion straight in the box, with Undo.** Rejected: an edit the owner didn't apply would be one Create away from Hermes.
- **Offer hub skills (`hub_skills`) and every skill the profile in use has.** Rejected: hub installs start subprocesses on the server, and a non-built-in skill isn't something a fresh profile has to keep. Copying own skills is Clone's job (ADR 0074).
- **Send the skill choice in the create, as `keep_skills` or `no_skills`.** Built first, then rejected. Hermes's `_disable_unselected_skills` (`hermes_cli/web_routers/profiles.py:153-174`) turns off every installed skill whose folder isn't listed, including built-in skills `GET /api/skills` hides on the platform, which the owner never saw. Against a real Hermes `f0d94882` on Linux, a create that unticked `arxiv`, `maps` and `songwriting-and-ai-music` also turned off `apple-notes`, `apple-reminders`, `findmy`, `imessage` and `sdlc-review`: eight off for three unticked. It also compares folder names with the front matter names the list shows, and is best-effort (a failure is logged and answered as `skills_disabled: 0`).
- **Trust `skills_disabled` and the toggle answers.** Rejected: both are best-effort or can be lost (ADR 0005, 0014); only a read of the new profile says what it has.
- **Accept toolset cautions on the owner's behalf, since the profile is new.** Rejected: an install and MCP coming back are effects on the server the owner must see first.
- **Roll back a partial result by itself.** Rejected: the owner may want to keep a profile that is mostly right; Delete is one click away.

## Consequences

- A new bot can now differ from Hermes's defaults in skills and tools without a trip to Settings, and each difference is read back before any success is said.
- The New form reads `GET /api/model/auxiliary` for the profile in use as it opens, and reads skills or toolsets only on Choose.
- Settings → Toolsets' caution words are in the catalogue (`toolsets.caution`) and shared with this form.
- Choosing skills costs, per listed skill the owner turned off, one `PUT /api/skills/toggle` and Settings → Skills' read back: `GET /api/skills` and `GET /api/config`, plus the SKILL.md of each skill listed by its path when the config's platform lists name a skill the list doesn't. That follows one read of the new profile's list. A skill already as chosen costs nothing more.
- A built-in skill Hermes seeds but doesn't list on the platform stays as Hermes sets it. The Choose hint says the list is what the profile in use lists, not every built-in skill.
