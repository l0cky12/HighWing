# Session frames leave the app through one SessionProtocol, and a rerun diff of recorded frames proves the legacy ones unchanged

> **Accepted.** Step 2 of ADR 0174's order of work. It changes nothing the app does: a canonical gateway is still refused at sign-in with the same words (ADR 0003, ADR 0044), and a legacy server gets the frames it got before, byte for byte. It changes two lines of ADR 0174: the session edits that go over REST are not operations of the interface, and the proof that legacy frames are unchanged is a diff that is run again, not a recording kept in the repository. The seam is `src/hermes/sessionProtocol.ts`. The proof is `scripts/frames-diff.mjs`.

ADR 0174 decided that support for Hermes's canonical session protocol is built behind the refusal, in steps that each change no behaviour. The first step after the map is an interface that every session call goes through, with only the legacy implementation behind it. Before this change the frames were built where they were sent: about twenty places in `transport.ts`, and in `bots.ts`, `toolsets.ts`, `commands.ts`, `goals.ts`, `skillCommands.ts` and one Diagnostics check in `capabilities.ts`. A canonical implementation needs one place to stand.

## Decisions

- **One `SessionProtocol` per connection.** `negotiate(gateway.ready, port)` picks it in `Hermes.dial`, once, when the socket opens. A reconnect or a profile switch opens a new connection and negotiates again. Until the first `gateway.ready` the transport holds a legacy protocol whose port refuses every call, because nothing is connected.
- **The refusal lives in `negotiate`.** It throws `ProtocolMismatchError` for a `gateway.ready` with `session_authority`, before anything is sent. Setup's connection test calls the same function with a port nothing leaves by, so the sign-in screen and the connection refuse the same servers with the same words. The step that lifts the refusal changes this one function.
- **One typed operation per thing the transport does to a session.** `open`, `resume`, `leave`, `submit`, `stop`, `command`, `configure`, `answer`, `openRequests`, `edit`, `info` and `approvalProbe`. `edit` takes a `SessionEdit` (rename, folder, branch, undo, compact, model), and each protocol answers it from a table with a row for every edit, so an edit one protocol lacks doesn't compile. Callers pass what they mean and get back what they read. No caller builds a session frame.
- **`LegacyProtocol` keeps nothing.** Each body is the expression its call site had, moved, with its keys in the same order, because `JSON.stringify` keeps insertion order and the proof compares text. The one memory it reads, which Approvals Hermes said are in its own queue, stays the transport's.
- **A protocol reads an answer as it arrives, never a turn later.** `Port.call` takes a `read` function, and the transport applies it to Hermes's result before the caller hears of it. A protocol that awaited the result and returned its own value would hand it on one turn of the event loop later, and the frame the transport sends next would leave behind frames it used to go before. The first version of this change did that, and `frames-diff` found 60 tests whose frames were the same and in another order.
- **A session method can't leave any other way.** `SESSION_METHODS` names every method whose row in `canonicalVerbs.ts` has a `canonical` note: the ones a canonical gateway refuses, and the ones it answers with another meaning. `Hermes.request` takes `Exclude<AppMethod, SessionMethod>`, and so do the helper modules' `rpc` types, so `this.request("session.title", …)` is a type error. Only the port handed to the protocol sends them. `sessionProtocol.test.ts` fails when the list and the map disagree, and when anything but the port calls the transport's unfenced send.
- **`shell.exec` is left out of the fence, by name.** Its rows have a `canonical` note, but the note says there is nothing to send instead: the canonical `shell.exec` runs only for a session, and the Bot Desktop's checks have none (ADR 0193). No session operation can cover it. The step that adds the canonical implementation decides what the Bot Desktop does there, and the step that lifts the refusal can't ship without that.
- **Inbound frames are read by the protocol, into two typed shapes.** `inbound(frame)` gives the transport `ask`, a question Hermes asks, or `event`. Answers to the app's own requests are matched by id before it, in the transport. The legacy protocol classifies a frame as `handle` did, so the transport's handling of each shape is the code it had. A canonical protocol will read its envelope and its `approval.request` and `clarify.request` events here.
- **REST session edits stay off the seam.** ADR 0174 listed "the session edits that go over REST" among the interface's operations, because a canonical gateway refuses a `PATCH` or `DELETE` of `/api/sessions/{id}` that names no `request_id` and `expected_revision`. The transport already names both on every such edit, read from `GET …/mutation-snapshot` (`fencedPatch`, `fencedDelete`, since Hermes v0.22.6 asked for them). That is the frame both protocols take, and it works for a chat this connection never attached, where a protocol would hold no revision. So rename, pin, archive, mark unread and delete are not operations of `SessionProtocol`.
- **The proof is a diff that is run again.** ADR 0174 asked for a test that records the suite's frames and compares them with the frames before the change. A recording kept in the repository would have to be made again by every change that adds a test, and a recording that is made again proves nothing. Instead `FakeHermes` can report each frame and dashboard call as the app sent it, a vitest setup file keeps them by test while `RECORD_FRAMES` is set, and `npm run frames-diff -- <base-ref>` runs the suite at the base ref and on the checkout and compares the two, test by test, in order. A changed, missing, added or reordered frame fails it, and so does a test the base ran that is gone. A test only the checkout has is listed.
- **A test whose frames differ is run again before it counts as changed.** Some tests send different frames from one run to the next on the same code: a poll or a capability check lands before or after another frame, which also moves the JSON-RPC ids after it. Two runs of the suite on one commit differed in 21 of 6,707 tests. So the files of the tests that differ are run again on both sides, up to five times, and a test is the same when one run at the base and one run on the checkout sent identical frames. A test no two runs agree on fails. Two random values are numbered in each run of a test, in the order they first appear: a UUID, and the random key `automations.ts` makes for a retry. So a frame that names another session, or a retry that stops reusing its key, still differs. The time of day in the name of a screenshot and of a pasted image is taken as equal. `--self-check` seeds each of these cases and shows the verdict, and runs with the suite.
- **`RpcError` keeps the error's `data`.** A canonical gateway says why in `data.reason`, and the fresh revision after a conflict in `data.revision`. Nothing reads it yet.

## Considered options

- **Translate legacy frames on the way out.** One function that takes the frame the call site built and rewrites it for a canonical gateway. Rejected: several legacy frames carry less than their canonical form needs (the turn's generation, the session's revision, an image's path), so the translator would need the call site's knowledge anyway, and nothing would stop a new call site from skipping it.
- **A fence of only the refused methods.** `clarify.lock`, `image.attach_bytes`, `image.detach` and `session.events.since` answer on a canonical gateway. Rejected: they answer with another meaning (ADR 0174 "4 answer, and mean something else"), which is the failure that shows no error.
- **Keep the helper modules on a raw `rpc`.** Rejected: a Bot Chat's title, an open chat's tool list, `/steer`, `/goal` and a skill would each need their own canonical branch later, outside the one module.
- **A committed recording, compared on every `npm test`.** Rejected above, and the tests that vary would fail it at random. The diff costs two suite runs, and is run by the pull requests of this work, each against the one below it.
- **Compare only the session methods' frames, or ignore the order of reads.** Rejected: either rule is a list of what not to look at, kept by hand. Running a differing test again needs no such list, and still compares every frame of a run in order.

## Consequences

- A change that sends a session method adds an operation to `SessionProtocol`, or uses one. It can't call `request`.
- A method that gains a `canonical` note in `canonicalVerbs.ts` fails `sessionProtocol.test.ts` until it is in `SESSION_METHODS`, and then fails to compile at each call site until that goes through the protocol.
- `bots.ts`, `toolsets.ts`, `commands.ts`, `goals.ts` and `skillCommands.ts` take the operations they need beside their `rpc`. Their tests hand them a `LegacyProtocol` over the same fake `rpc`, so they still assert the legacy frames.
- `ProtocolMismatchError`, `RpcError`, `ConnectionLostError` and `LIMITS` are defined in `sessionProtocol.ts`, and `transport.ts` still exports them. `SignInFailure` is in `signInFailure.ts`, so that Setup can call `negotiate` without an import cycle, and `setup.ts` still exports it.
- `frames-diff` needs the base ref to have the recorder, so the earliest base is the commit that added it. It takes two runs of the suite, and more for the tests that vary.
- It proves only what the suite sends. A frame no test sends is covered by `sessionProtocol.test.ts`, which holds each operation's legacy frame as text, apart from a message's attachments, which the suite sends. A frame that only some runs of a test send could change unseen in that test, when no other test sends it.
- Nothing changes for the owner.
