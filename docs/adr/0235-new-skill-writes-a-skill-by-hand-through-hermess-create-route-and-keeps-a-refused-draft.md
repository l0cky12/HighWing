# New skill writes a skill by hand through Hermes's create route, and keeps a draft Hermes refuses

> **Accepted.** It amends ADR 0030, which kept creating a skill out of Settings → Skills. Installing skills from the Skills Hub stays out. The code is `SkillsApi.create`, `newSkillProblems`, `newSkillText` and `renamedInFrontmatter` in `src/hermes/skills.ts`, and `NewSkillEditor` in `src/ui/SkillSettings.tsx`. Tested in `src/hermes/skills.test.ts` and `src/ui/skillSettings.test.tsx`, against `src/hermes/fakeSkills.ts`. Issue #33.

The owner knows a procedure a bot should follow every time, such as how to cut a release or how to triage a ticket, and wants to write it down as a skill. Settings → Skills could list, switch, edit, copy, move and archive skills, but not create one, so a new skill needed a shell on the server or a request to the bot. ADR 0030 ruled creating out. Its stated concern is installing from elsewhere, which fetches and runs outside code. A SKILL.md the owner types doesn't do that. ADR 0118 already sends `POST /api/skills` to copy a skill, so the route, its relay rule and Hermes's checks are in use. The owner approved amending ADR 0030 for this.

## Decisions

- **New skill, in the list's toolbar.** It opens a form in place of the list: a name, an optional category, and SKILL.md in a plain textarea. The SKILL.md starts as the front matter Hermes writes for its own skills (`agent/learn_prompt.py`: `name`, `description`, `version: 0.1.0`), then empty `## When to Use` and `## Procedure` sections. The category field suggests the categories the profile's skills already use. Skill text stays data, as ADR 0030 says: shown only as text, never rendered or run.
- **The front matter name follows the name typed.** Hermes lists a skill, and the composer runs it, by the name its front matter declares, while the folder takes the name sent. So the two have to match. While the front matter's `name:` still says the name typed before, typing in the name field changes it too. Once the owner writes another name there, it's left alone, and the form asks for the two to match.
- **Checked before sending.** The checks are Hermes's own, as far as this app can foresee them. The name and category must each be one folder name that `VALID_NAME_RE` allows (`_validate_name`, `_validate_category`). The front matter and size checks are the same as an edit's (ADR 0030). The front matter `name:` must be the skill's name. The `description:` must be written in, because Hermes reads an empty one as YAML's null and would store the text "None". The form lists what to fix, and Create skill stays off until nothing is left. Nothing to fix is shown before a name is typed.
- **Sent through the copy's route and relay rule.** Create sends `POST /api/skills?profile=` `{name, content}`, plus `category` when one is given. The Rust relay's `skill_create_allowed` already passes exactly that body, so it doesn't change. Hermes's `_create_skill` runs its name, front matter, size and opt-in security checks. It refuses a name the profile already has, and writes SKILL.md only. The skill lands in the profile's skills folder, or in the folder `skills.create_dir` names.
- **A refusal keeps the draft.** Hermes's 400 is shown as Hermes words it, such as "A skill named 'github' already exists at …" or a security scan's block with its findings, and the form keeps the name, category and text, to fix and send again. A lost answer, a 5xx or a deadline is settled as a copy's is (ADR 0118): the app reads the skill back, and it counts as created only if Hermes has exactly the text sent. Copy and Create share that code (`SkillsApi.post`).
- **Created means read back and listed.** Once the read-back matches, the list is read again and the new row says where Hermes wrote the file. It also gives the `/name` the composer runs it by. If the profile's `skills.disabled` list already names the skill, from an earlier one of that name, the row is off, and the note says so and points at its switch. The app doesn't turn it on unasked. A write here makes the composer read its skills again (ADR 0030), so the new skill is in the `/` menu at once.
- **A draft can't be lost by accident.** All skills, Cancel, and everything that asks before dropping an unsaved edit (leaving Settings, changing tab, switching profile, signing out, closing the window) ask before dropping a draft with anything typed in. An untouched form closes without asking.

## Considered options

- **Import a SKILL.md file** (the issue's approach 2). Not now. It sends through the same route and can follow this, but a skill with scripts or references still needs Server files for the rest.
- **Draft it with AI** (approach 3). Not now. ADR 0197 turned down writing a persona from nothing, and the same concern may apply here.
- **Separate fields for the description and the steps,** with the app writing the front matter. Rejected: Hermes's front matter takes more fields than these (`version`, `platforms`, `metadata`), and the editor already works on the whole SKILL.md text. One text that is exactly the file keeps what's sent and what's read back the same.
- **Check the 60-character description limit before sending.** Hermes at `f0d94882` refuses a new skill whose description is longer than its skill index shows, but `bf0203a` takes it. The form says so in its note and shows Hermes's refusal, as ADR 0030 does for an edit.
- **Write SKILL.md through Server files.** Rejected, as in ADR 0030: it skips Hermes's checks and its index cache.

## Consequences

- Settings → Skills can create a skill as well as list, switch, edit, copy, move and archive one. It still can't rename one, delete one outright (archiving is Hermes's delete), or install one from the Skills Hub.
- Only SKILL.md is written. Files under `references/`, `templates/`, `scripts/` or `assets/` go up through Server files afterwards, and an edit's check of the files the body names then applies.
- A server without `POST /api/skills` (`bf0203a`) answers 404 or 405, and Create says this Hermes can't create skills. Listing, switching and editing still work there (ADR 0118).
- Hermes's own YAML parse and security scan have the last word. A draft the form lets through can still be refused, and the refusal is shown with the draft kept.
- Verification: the tests run against the fake's create route, which follows `_create_skill` at `f0d94882`, with a settable security scan refusal. `e2e/features/new-skill.e2e.tsx` drives the form in headless Chromium.
